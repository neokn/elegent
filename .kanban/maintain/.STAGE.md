# maintain

A card in maintain/done/ is finished: its change is reviewed, tidied and merged
into the base branch, the documentation says what the repository holds with
the change in it, as the maintainer accepted, and the card's trail — how the
change got there — is in the repository beside its story. A card in
maintain/pending/ has that work done in its worktree and waits for the
maintainer.

## Do
Work in the card's worktree, `build.worktree`: the change is not in the main
tree until this stage accepts it. Run the `maintain` skill there, in change
mode, on the change the
card's `build.commits` make — every attempt's commits — with the story the
card's `refine.artifacts` names, the `spec.md` and specification files of
`specify.artifacts`, and the plans of `design.artifacts`, whose `Architecture
basis:` line names the documentation to keep true. `.kanban/` is the board's own
path: never documentation, and never written. Write nothing outside the
worktree, and commit nothing: the maintainer has not seen it yet. A question
only a person can settle — an Observation's, whether the code is a defect or the
rule has changed — is not asked here: it goes into the report for the
maintainer.

Before the documentation work, run the `flowmap` skill in the same worktree, in
change mode, on the same change: `base` is the parent of the first commit in
`build.commits`, or the start commit (below) when the branch holds a
`merge(<card id>):` commit, `head` the last, and every entry of `build.commits`
but a `merge(<card id>):` one is a commit of the change (by subject when its sha
was rewritten). Hand it the story as a
source labelled `story`, the `spec.md` and specification files labelled `spec`,
the plans labelled `plan`; the card's `review` record as its review (`verdict`,
`summary` as the reason, `findings` with `file_line` as `where` and `fix` kept,
`security`, `departures`, `follow_ups`), `build.flagged` as what the implementer
disclosed, `build.test_command`, `build.test_result` and `build.acceptance_tests`
with `test.evidence` as its verification; the review gate event's `evidence` as
the reviewer's checklist. Its two files go beside the story file
`refine.artifacts` names, as `flows.html` and `flows.json`, and are this stage's
artifacts like any documentation it writes. flowmap draws with what the machine
has and falls back to Mermaid source: never run its `setup` here, it writes
outside the worktree. A flowmap check that fails is reported in `flowmap` and
does not stop the stage.

On a card whose last maintain was rejected, the work is that attempt again: the
files it wrote are still in the worktree, and the maintainer's reason is in
its gate event. A card that came back after a base check (below) may still hold
that check's preview merge in the worktree: the base check undoes it first.

Then work out the **tidy**: the commits the card's branch will hold once it is
tidied, from its **start commit**, with the same final tree. The start commit is
the newest base commit a `merge(<card id>):` commit on the branch brought in,
else `build.base`'s commit:
1. the input documents' `docs:` commit, each bootstrap `chore:` and each
   `existing` refactoring commit, as they are;
2. per plan, in design's order, one `test:` commit — the plan's test files, every
   attempt's — and one `feat:` commit — the rest of that plan's change, every
   rework's fix included. When one file holds the work of two plans,
   those plans get one pair between them, named for both. Each `feat:` commit's
   body holds the Attention list the gate shows (§ Gate) and, last, one line on
   how to undo it: `Revert: revert this plan's test: and feat: commits together;
   the original commits are on backup/<card id>` — that branch never leaves the
   machine, so the line names it rather than promising it. A `merge(<card id>):`
   commit is not carried: the start commit already holds what it brought in;
3. this stage's documentation commit.
Each message keeps the scope `(<card id>)`.

Write each row of `review.do_not_report` into the project's `REVIEW.md`, § Do
not report, in the worktree and uncommitted, like every other file this stage
writes. A project with no `REVIEW.md` gets no row: the rows stay in the record,
and the report says so.

Last, the **base check**. The test and review verdicts this card carries were
given on `build.base`, or on the base a `merge(<card id>):` commit brought in:
the start commit. They are not a verdict on the tree the merge will make. When
a preview an earlier pass left is in the worktree, undo it
(`git merge --abort`). Then, from the main tree, compare the base branch
`build.base` names (`git rev-parse <branch>`) with the start commit. When they
are the same, the base has not moved, and the check ends there. When the base's
commit is the `now` of this card's earlier `base_check`, and the card was
returned to test after that check, test and review have judged this merged tree
already: the check records no hit and ends there. When the base has moved past
what they judged, preview the merge in the worktree:
`git merge --no-commit --no-ff <branch>`. Nothing is committed. Then check two things:
1. **callers**: list every symbol the card's change deletes or renames, read
   from the diff of `build.commits`. Search the base's new commits for each
   name (`git diff <start commit>...<branch>`). Every new caller is a hit.
2. **changed**: in the previewed tree, `git diff card/<card id> -- <every file
   the card's change touches>`. Every file that diff shows is a hit.
A preview that conflicts is undone at once (`git merge --abort`); its
conflicted paths are the check's result. A check with no hit undoes its preview
too. A check with a hit leaves the preview in the worktree, uncommitted, for the
gate.

## Record
- `attempt`
- `artifacts`: every file the report lists as written, flowmap's `flows.html` and `flows.json`, `REVIEW.md` when it got a row, and the trail `trail.md` the gate writes on an approve (§ Gate); on a rework, every file written in any attempt that still differs from `HEAD`
- `flowmap`: flowmap's report — `html`, `json`, `revision`, `base`, `flows`, `stations`, `refs_verified`, `unverified`, `open_checkpoints`, and `failed` with the check that failed when it wrote nothing
- `summary`: one line per file edited, and one per item owed
- `drift`, `owed`, `records`: as the report gives them
- `open_questions`: every question the maintainer must settle, each with the
  answer maintain recommends
- `tidy`: the branch's commits before and after, as two lists of `<sha> <subject>`
  (the after list as planned, its shas once made), and `backup: backup/<card id>`
- `base_check`: `{branch, start, now, callers, changed, conflict}`: the base
  branch, the start commit, the base's commit when the check ran, each new
  caller as `{symbol, file_line}`, each file the previewed diff shows, and each
  conflicted path. When the base has not moved, `now` is `start` and the lists
  are empty
- `merged`: the base branch and the commit it reached, once brought back

## Gate
When `base_check` has a hit or a conflict, say so first: what moved, and that
test and review judged the tree without it. A hit: recommend returning the card
to test, so test and review are earned again on the merged tree. The return is
kanban's Return: a `returned` event from maintain to test whose `reason` names
the callers and the files that moved, and the move into test/doing/. The
preview stays in the worktree for them. The maintainer answers "not now" and
returns the card. Or the maintainer approves the card as it stands, and the
gate event's `evidence` names what moved. A conflict: recommend returning the
card to build the same way, with the reason "merge the base in" and the
conflicted paths. A conflict is never approved past, and never left as a
`git merge --abort` and a stop.

Before asking the maintainer, compose the **Attention** list from the card's
`build`, `test` and `review` records. It opens with the change's risk,
`review.risk` and `review.risk_reason`, which says how closely to read the rest:
- `low`: the maintainer may approve on the Attention list and the diff stat;
- `medium`: the Attention list and every written file's diff, as below;
- `high`: as `medium`, and the gate asks the maintainer to name a second person
  who read the change. The gate event's `evidence` records that name. The
  executor does not check it: it is the maintainer's word, as the approval is.

The list then holds:
- each departure and its decision: `build.departures` with `review.departures`'
  `decision` and `reason`;
- each finding build declined: the `build.answers` entries whose `outcome` is
  `declined`, with their `reason`;
- what build flagged and left undecided: `build.flagged` and `build.undecided`;
- each survivor test could not pin: a `SURVIVED` row of `test.evidence` that no
  `test.mismatches` entry names;
- the attempt counts: `build.attempt`, `test.attempt` and `review.attempt`,
  and each `approach` the evidence of a rejected `review` gate event holds.
An empty item is left out. Show the list with the documentation diff. A host
with no card pane shows nothing else: the gate text carries the list.

Open `flows.html` for the maintainer (`open <path>`): the change as flows,
station by station, with its diff, the sentences of the story and the
specifications it realises, and the open checkpoints. Then show every written
file's diff (on a rework, the diff of every file in `artifacts`), each
Observation with its question and answer, what is owed, the records the change
made untrue, the tidy: the branch's commits now and the commits it will hold,
and each `review.do_not_report` row with the diff of `REVIEW.md`. Their word is
the verdict on all of it; record it and nothing more. An approve lands every
`do_not_report` row the maintainer did not strike in their answer.

The recorded work goes to maintain/pending/ with its `completed` event and
waits there; the maintainer decides on a card in pending/.

On an approve, before the gate's transaction, from the main tree, in this order.
A step that fails stops: the card stays in maintain/pending/ with a `comment`
naming the step and its output, and the person decides. First, the main tree
holds nothing the merge would overwrite: an untracked or modified file the
card's branch also carries stops, and the comment names each one. Then the base check
again. A `base_check` whose `conflict` is not empty stops here, and the comment
recommends returning the card to build with the reason "merge the base in".
Otherwise undo a preview it left in the worktree, when one is there
(`git merge --abort`), and when the base's commit is no longer
`base_check.now`, run the check once more. A hit or a conflict stops, with nothing committed and nothing rebuilt: a hit's preview
stays on the card's tree, and the comment names what moved and recommends the
return the gate recommends. A check with no hit undoes its preview, and the
steps go on.
1. **The trail** — the card is the record of how this change was decided, and
   the board is not in git by default, so the repository keeps a copy. In the
   worktree, beside the story file `refine.artifacts` names, write `trail.md`
   with kanban's renderer, from the card as it stands now, with the decision
   this gate is about to record as its last line:
   `python3 "${CLAUDE_PLUGIN_ROOT}/skills/kanban/scripts/card-trail.py" .kanban/maintain/pending/<card id>.yml --decision "approved by <the maintainer's principal>[, second reader <name>]" > <worktree>/<story dir>/trail.md`, run from the main tree, where the board is.
   It holds the requirement as typed and where it came from, every history
   event and every stage's record —
   the findings, the declined ones, the test evidence, the attempts. The gate
   event itself, `tidy`'s shas and `merged` are written to the card after this
   commit, so the trail ends with the decision line; a later `kanban status`
   shows the rest. Add `trail.md` to `maintain.artifacts`.
   **Documentation commit** — in the worktree, first take out of `REVIEW.md`
   each `do_not_report` row the maintainer struck. A `REVIEW.md` left as `HEAD`
   holds it is dropped from `maintain.artifacts`. Then
   `git commit -m "docs(<card id>): keep the documentation true" -- <maintain.artifacts>`.
   The trail is always in it, so every approve makes this commit.
2. **Backup** — `git branch backup/<card id> card/<card id>`: the original
   commits, as they were. This stage never deletes it.
3. **Tidy** — rebuild `card/<card id>` as the tidy planned, each `feat:`
   commit's body holding the Attention list. Then check:
   `git diff backup/<card id> card/<card id>` is empty, and `build.test_command`
   passes at each `feat:` commit and fails at each `test:` commit that holds a
   test build saw red. A check that
   fails puts `card/<card id>` back at `backup/<card id>` and stops.
4. **Bring back** — on the base branch `build.base` names, in the main tree:
   `git merge --ff-only card/<card id>`, or `git merge --no-ff card/<card id>`
   when the base has moved; then run `build.test_command` on the merged result.
   A conflict (the base moved again since the check) is undone
   (`git merge --abort`), `card/<card id>` goes back to `backup/<card id>`, and
   the comment recommends returning the card to build with the reason "merge
   the base in"; a failing suite is a stop, the merge left for the person.
5. **Clean up** — `git worktree remove .worktrees/<card id>` and
   `git branch -d card/<card id>`. The backup branch stays.

Then one transaction: the record with `tidy` and `merged`, the `gate` event
naming the backup branch and the merged commit in its `evidence`, and the move
from pending/ to done/. It makes no commit of its own. A rejection changes no
branch: the card goes back to maintain/doing/ for a new attempt in the same
worktree, with the maintainer's answers to its open questions in the gate
event.
