# review

A card in review/done/ has a change a reviewer who did not write it traced from
its story through its specifications and plans to the diff, and approved.

## Record
The review's report, as it gives it:
- `attempt`
- `artifacts`: `[]` — the review writes nothing
- `summary`: the verdict, its reason, and one line per Important finding
- `verdict`, `return_reason`, `sub_verdicts`, `security_sensitive`, `risk`,
  `risk_reason`, `findings`, `declined`, `security`, `departures`, `guardrails`,
  `do_not_report`, and `approach` when the review gives one
- `follow_ups`, with the security pass's `security.follow_ups`: opened as build's
  `## Record` opens them, security ones first
- each `guardrails` entry: opened as build's `## Record` opens a follow-up, as a
  technical item. It is a child card in backlog whose `labels` hold `technical`,
  with a comment on this card naming it. Its description says the rule, the
  control proposed and where it lives (`target`), the finding it cites with that
  finding's `file_line`, and its Red: the new check must fail on the code of that
  old finding before it passes on the fix

The gate event's `evidence` lists every Important finding, one line each — pass,
`file_line` and what is wrong — so later reviews can read them as history, and
the review's `approach` when it gave one, so it outlives the next attempt's
record. The
record's `declined` keeps the rest of that history: every finding the reviewer
raised and then dropped on its own re-check, each with the finding, the rule it
was raised under, and the reason it was dropped.

The review writes no file but the card: a departure it accepts is a decision in
`departures`, and the trail maintain writes carries it. A `do_not_report` row is a proposal in the record too: it lands in
the project's `REVIEW.md` only when maintain's maintainer approves it. The
change is not merged here: it goes back to the main tree when maintain accepts
it.

## Gate
Run the `review` skill inside the card's worktree, `build.worktree`, never in
the main tree, telling it to edit nothing: it reports each decision.
The change it reviews is what the card's `build.commits` make — the
commits of every attempt after the first are the returned fix — with the story
the card's `refine.artifacts` names, the `spec.md` and specification files of
`specify.artifacts`, and the plans of `design.artifacts`. The
implementer's claims are `build.cases`, `build.acceptance_tests`,
`build.superseded`, `build.departures`, `build.follow_ups`, `build.answers`,
`build.flagged`, `build.undecided` and `build.outside_skeleton`; the
independent evidence is `test.verdict`, `test.evidence`, `test.mismatches` and
`test.follow_ups`. The review contract is the project's `REVIEW.md`, when it
keeps one. The review history is the evidence of every rejected `review` gate
event on the board's cards, `archive/` included: the Important findings of
earlier reviews. It is also the `review.declined` of every card on the board,
`archive/` included: the findings earlier reviews dropped, for the skill's
Do not report proposals. On a card that came back, this card's own rejected
`review` gate events are its earlier findings, and `build.answers` is the
implementer's answer to each: the skill raises again only what the fix did not
resolve. A card maintain returned after its base check holds the
base branch merged into the worktree, uncommitted: review the change as that
merged tree holds it.

`approve` is approved. `block` is rejected, and the card goes back to build.
