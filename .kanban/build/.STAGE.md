# build

A card in build/done/ has code and tests realising every plan design accepted,
committed, with the one command that proves them green.

## Do
The change is built in a git worktree of its own, never in the main working
tree: `.worktrees/<card id>/` on the branch `card/<card id>`. On the card's
first pull into build — it has no `build.worktree` yet — run, from the main
tree, `git worktree add -b card/<card id> .worktrees/<card id>` at its `HEAD`,
and add `.worktrees/` to the exclude file `git rev-parse --git-path info/exclude`
names when it is not there (in a linked worktree `.git` is a file, so the
literal path `.git/info/exclude` does not exist). The glossary is already
committed at refine's and specify's gates. The story folder refine,
specify and design wrote — the paths their `artifacts` name — is in the main
tree and not in `HEAD`: move it into the worktree, leaving no copy in the main
tree, and commit it there first, `docs(<card id>): story, specifications and
plans`; the merge brings it back. `.kanban/`
stays in the main tree, and every board transaction runs from there. A card that
came back is reworked in the same worktree. Never rebase or amend on the card's
branch: a rework adds commits.

Run the `build` skill, inside the worktree, on each plan the card's `design.artifacts` names — the
files under `plans/`, in that order — with the card's id as the commit scope and
`.kanban/` as the board's own path, which build never writes, stages or commits.
Other work may share this machine: end only a process you started, by its PID,
never by name (`pkill -f`, `killall`); a hung test run is run once more, not
killed by name.
The card's live `design` approval is the acceptance of those plans, their
decisions included: say so, naming its approver.

On a card that came back — its latest `returned` event sends it to build — the
work is the rework: the same plans, with the record of the stage named in that
event's `from` as what came back — `test.mismatches` and `test.follow_ups`; or
`review.findings`, `review.security.findings`, `review.departures`,
`review.follow_ups`, `review.security.follow_ups` and `review.approach`; or, from maintain, its
`base_check`, with the reason "merge the base in". That one is done first, in
the worktree, before the build skill runs: `git merge <the base branch>`,
resolve every conflicted path, those `base_check.conflict` names and any the
merge adds, the way the build skill's `references/rework.md` § Merging the base
in says, and commit the merge as `merge(<card id>): bring the base in`. A
merge adds a commit; it is never a rebase. Then the build skill reworks the card with one item: every case green
again on the merged tree. A card that comes back to build a second time from the same stage, test or
review, is one return from blocking: tell the build skill so, and hand it every earlier
return's items with their answers, so it steps back before it fixes
(`references/rework.md` § When the fixes do not converge). When you are
handed the report of an earlier build that stopped, continue from the files it
touched.

## Record
- `attempt`
- `worktree`, `branch` and `base`: the worktree's path, `card/<card id>`, and
  the main tree's branch with the commit the worktree started from, as
  `{branch: <name>, commit: <sha>}` — written on the first attempt, kept after
- `artifacts`: every acceptance test the builds wrote, all attempts
- `summary`: one line per plan, and each departure's title
- `commits`: every commit this card's builds made, all attempts, oldest first,
  each as `{commit: "<sha> <subject>", attempt: <n>}`. Take them from git and
  from the reports, as one list without duplicates:
  `git log --reverse --fixed-strings --grep='(<card id>):' --format='%h %s' <base commit>..card/<card id>`
  (the range keeps out every commit that is not this card's branch; a
  `merge(<card id>):` commit is the card's, and the base's own commits it
  brings in are not), without review's `docs(<card id>): accept` and maintain's
  `docs(<card id>): keep the documentation true` commits. A commit that no
  report of this record names carries the attempt its stop comment gives, or
  else this attempt.
- `test_command` and `test_result`: the one command that runs the suite, and its
  latest result
- `acceptance_tests`: each specification file with its acceptance test
- `cases`: every scenario and case with its test, Red and Green, grouped by plan,
  all attempts
- `superseded`: all attempts, the latest entry for each scenario or case standing
- `departures`: all attempts, dropping any a later rework removed as declined
- `flagged`, `undecided`, `outside_skeleton`, `own_story`: as the reports give
  them, all attempts
- `answers`: every attempt's answers, each marked with its attempt and the stage
  whose items it answers
- `follow_ups`: all attempts, each with the id of the card it opened. A new one
  is opened in this transaction as a follow-up card in backlog —
  a child of this card whose description says what is wrong, its evidence, what
  must be refined again, and the story and specifications of this card's
  `refine` and `specify` records, and whose `labels` hold `security` when the
  report marks it `security: true` — with a comment on this card saying the same
  and naming it. One whose evidence names the same place as a follow-up this card
  already names is not opened again. When a rework fixes what a follow-up this
  card opened describes, the same transaction appends a `comment` to that
  follow-up naming the commit; archiving it stays a person's decision.

A report that stops is not recorded and finishes nothing: append a `comment` to
the card with its `stopped` reason, its commits and its `touched` files, and the
card stays in build/doing/. The same comment holds every report of this run that
finished before the stop. The next record of this card carries those reports
and those commits forward, each under its own attempt. A stop on a question is
asked and run again at once (kanban `run`); whichever build runs on this card
next is handed that report.

## Gate
None. What the developer claims is not proof of anything; test verifies it next,
in a context that never saw it built.
